# Verify Gateway traffic and administrative reporting

Enable Gateway traffic control with `Traffic__Enabled=true` and configure `Traffic__SigningKey` with at least 32 random bytes encoded as Base64. Use the same key and Redis instance across Gateway replicas. Apply Catalog migrations and the reporting section of `services/ticketing/001_tickets.sql`. Keep the Catalog and Ticketing service listeners private.

- Run `pwsh tests/load/verify-gateway-shedding.ps1` with traffic enabled and a test IP limit low enough to produce 429 responses. Checkout routes have independent Redis rate counters and bypass the waiting room.
- With a customer token, poll `POST /api/v1/waiting-room/admission`; submit a hold with the returned header and resend the same grant to check rejection.
- Use an ADMIN JWT for Catalog list, PUT and DELETE operations at `/api/v1/admin/catalog/{resource}`. PUT takes the resource fields without the ID. List returns at most 100 rows and accepts `offset`. A write and its audit row commit together.
- Use an ADMIN JWT for `GET /api/v1/admin/reports/overview`. Sales join order and payment events. Occupancy and active-hold segment counts reflect the Booking event projection. Lag is the reporting consumer group's sampled lag. DLQ figures include Catalog projection dead letters and Ticketing delivery failures.

US-09 pressure polling uses the private Booking Engine endpoint `GET /internal/v1/traffic-pressure`. Thresholds are configurable under `Traffic`. Defaults are 80% PostgreSQL pool utilization, 500 pending holds, two seconds for the oldest pending hold, 10,000 active physical holds, 200 ms broker write latency, and 100 ms Redis ping latency. Stale or unavailable samples stop new hold admission. The checkout lane keeps independent quotas and permits up to 16 concurrent requests per Gateway instance. Set `TRAFFIC_TEST_REDIS` to an isolated Redis database and run `dotnet test tests/gateway` to verify FIFO, scoped grant replay and expiry, and checkout under concurrent browse load.

The admission policy also checks Kafka partition skew (the largest minus smallest partition offset increase per sample, default 200), Redis used memory as a percentage of its configured maxmemory (default 85%), and checkout requests admitted per Gateway sample (default 50). The settings are `Traffic__KafkaPartitionSkew`, `Traffic__RedisMemoryPercent`, and `Traffic__CheckoutRequestsPerSample`. Redis must permit `INFO memory`; configure maxmemory to enable the percentage threshold. For a live checkout check, supply `TRAFFIC_TEST_ORDER_URL` for an existing test order and `TRAFFIC_TEST_ORDER_OWNER` for its owner UUID alongside the isolated Redis test connection.

The admin overview returns three sections. `data` contains the Ticketing read model. `traffic` contains local Gateway pressure when traffic control is enabled. `booking` contains the latest private Booking sample when available, including PostgreSQL pool utilization, queued work, Kafka produce signals and `logicalActiveHolds`. The logical count includes standalone holds and counts a multi-carriage saga once. It is capped at 10,001 per sample. Lag reports the reporting group's committed offsets and includes a sample time.

For integration verification, run `dotnet test tests/catalog` with `CATALOG_ADMIN_TEST_DATABASE_URL` set to a disposable PostgreSQL connection. For the live reporting Kafka test, set `REPORTING_TEST_DATABASE_URL` to a separate disposable database and `REPORTING_TEST_KAFKA` to an isolated development broker. The test creates a disposable dead-letter topic, publishes one synthetic record, and deletes the topic after verification.
